# 第 18 步：三进程集群故障验证

本步验证真实 gRPC 集群在网络隔离、单向丢失、延迟、丢包、重复、乱序与进程崩溃时的行为。三个节点仍是独立的 kvnode 进程，各自有 Store、Raft 状态和数据目录；测试控制器负责转发消息和检查结果。

## 改了什么

| 文件 | 作用 |

没有增加 Raft 成员。存储引擎、Raft 协议、磁盘格式、客户端成功语义和 proto 都沿用原实现。本轮没有发现需要修改协议或存储逻辑的问题。

## 为什么需要可选路由

正常情况下，节点从 members 读取监听端口和对端地址，直接互相发送 Raft 消息。测试时只替换出站目的地址：

```text
节点 A 的发送线程
  → 给节点 B 的转发端口
  → 测试队列：按规则丢弃、延迟、重复或调整交付顺序
  → 节点 B 的真实 RaftTransport.Deliver

节点 B 的协议回复
  → 给节点 A 的转发端口
  → 节点 A 的真实 RaftTransport.Deliver
```

每个目标有一个转发端口，共三个，由同一个测试控制进程管理。转发器只保存消息和调度状态，没有 Raft 日志、不投票、不计入多数派。

members 继续提供真实的节点监听地址，客户端和管理工具直接访问这些地址，因此被隔离的旧 Leader 仍能接收查询。这能区分“节点被杀死”与“节点活着但无法联系多数派”。

默认 raft_routes 为空，运行路径与此前相同。配置路由时必须覆盖与 members 完全相同的三个成员 ID，地址仍为不同的本机回环端口；它只改变消息下一跳，不改变成员配置。

--raft-routes 的值与 --members 一样使用 ID=127.0.0.1:PORT 列表。测试程序会自动创建转发器并传入参数；正常启动集群不需要这个选项，也没有运行时的生产丢包、延迟管理接口。

## 转发器如何工作

收到 Envelope 后先检查目标和来源，按 from/to 对应的有向链路查规则：

1. blocked 或命中固定的丢包周期：不交付消息。
2. 否则把完整消息复制到按交付时间排序的优先队列。
3. 配置重复时，再放一份稍晚交付的副本。
4. 转发线程等最早任务到期，再用新的 gRPC 调用交给真实节点。

接收方拿到的仍是原始 Envelope，消息的 rpc_id、任期、日志条目都不改。转发器立即返回的 Empty 仅表示传输接收，不能作为 Raft 的多数派确认；真正的投票/复制回复仍通过反方向的另一条消息交付。

每个目标有独立转发线程，给失联目标的请求最多等 250ms，不挡住另外两个目标。队列每个目标最多 256 项、8 MiB 编码字节，超额作为额外丢包记录；本轮混合故障序列要求没有发生队列溢出。

混合序列按链路计数决定丢第几条、复制第几条和奇偶延迟，不依赖随机概率。两个配置使用不同的丢包和复制周期；较早消息的较长延迟允许后来的消息先到达。实际交付顺序、重复、丢包及延迟都有计数，测试断言这些情况确实发生；切换规则时旧代队列项的丢弃也计入 dropped。规则固定，但实际线程时序并不完全确定。

## 切换隔离状态时为什么要等

为防止“设置了隔离但旧消息仍在飞”，每条链路保存一代 generation：

- 更新规则时递增代数，旧队列项在出队时被丢弃。
- 进入真实转发 RPC 前计数 in_flight，完成后归还。
- 设置 blocked 后，等待受影响链路原有的转发调用结束，再让隔离操作返回。

因此隔离完成后发起的新提议不能借用切换前尚未送完的消息获得确认。恢复网络时也会丢弃旧代队列项，靠 Raft 心跳重新发送；本测试不是保留所有旧报文的网络模拟器。

调度状态用一个 mutex 保护。condition_variable 等待期间释放锁；实际网络 RPC 不持有调度锁。等待优先队列的时间点先复制到局部变量，避免其他线程入队导致容器重新分配后继续引用旧元素。

## 七类场景

| 场景 | 操作 | 验证内容 |
| --- | --- | --- |
| 隔离旧 Leader | 双向切断它与其他两人的链路，保留客户端入口 | 多数派选出更高任期 Leader 并写入 Bob；旧节点仍有 Alice，却不能返回一致性旧读或确认新写；恢复后旧节点退位，未提交冲突后缀被修正 |
| 隔离 Follower | 切断一个 Follower，另外两个继续更新和删除 | 多数派继续服务；落后节点恢复后覆盖旧版本并执行删除 |
| 单向丢失 | 阻断其他节点发给 Leader 的 Raft 消息，保留相反方向 | 仍能发送心跳，但新条目不能因本地追加就确认；恢复回复路径后，先前的 Unknown 可以提交 |
| 完全分区 | 六条有向链路全断 | 没有节点能推进已保存提交位置；Get 不退回本地旧读；恢复后继续成功读写 |
| 延迟、丢包、重复、乱序 | 两组固定周期，对全部链路调度消息并执行混合更新/删除/读取 | 正确处理重复和旧回复；成功读取不返回错误的已知值；恢复后与独立模型一致 |
| 崩溃与分区组合 | 一个 Follower 隔离时强杀 Leader，之后恢复网络、重开旧节点、再全体重启 | 无连接多数派时不服务；恢复后重新确认写入；所有 Store 保留已确认数据并恢复一致性读取 |
| 错误路由 | 未知成员 ID、重复地址、不完整路由 | 返回参数错误，拒绝在错误配置下创建数据目录 |

## 怎样判断正确，而不只是“程序没崩”

每次成功写入必须得到 ClientCode::Ok 和有效提议编号。隔离少数派时直接调用其客户端 RPC，检查不能返回 CLIENT_OK；同时用 local-get 确认它确实还持有旧数据。

混合序列使用独立 map 记录已确认的最终值或删除状态。写入返回 Unknown 时，不假设它成功或失败，暂时移除该 key 的确定预期；后续已确认写入可重新确定该 key 的状态。没有提交任何写入的 Unavailable 不修改模型。

恢复通信后，检查三个节点的本地值、删除结果、commit_index 和 last_applied 收敛。未提交的额外日志尾部可以暂时保留，所以不错误地要求所有 last_log_index 总是相等。组合崩溃场景还在全体重开后检查已确认数据。

这些是有限故障序列和有限 key 的实现验证，不是全历史线性一致性检查器或形式化证明。测试不使用系统防火墙、不修改用户网络，只向自己启动的子进程发信号；临时目录、节点和转发线程由 RAII 回收。

## 如何运行

所有命令在项目根目录执行。已经有本地 gRPC 依赖时，配置并构建：

```sh
cmake -S . -B build/network -DKVSTORE_BUILD_GRPC=ON -DBUILD_TESTING=ON -DCMAKE_PREFIX_PATH="$PWD/build/deps/install"
cmake --build build/network
```

单独运行本步，显示场景及故障计数：

```sh
ctest --test-dir build/network -R '^cluster_fault$' -V --output-on-failure
```

测试会自动选择空闲端口，启动三个节点和转发器，执行场景并清理，不需要先手工启动集群。成功时输出 All 7 cluster fault tests passed。

完整回归：

```sh
ctest --test-dir build/network --output-on-failure
```

## 验证结果与范围

新增一个 cluster_fault CTest 组，包含七个测试函数，其中混合消息故障函数运行两个固定配置。首次单独运行通过，29.72 秒；两组都确认了 10 次写入，丢包计数 23/28、重复交付计数 37/41、乱序计数 84/109。这些计数会受线程调度、选举和重发影响，不是每次完全相同的期望输出。

完整回归结果如下，原有测试全部保留并通过：

| 构建 | CTest 结果 | 总耗时 |
| --- | --- | --- |
| 默认构建，不启用 gRPC | 19/19 组通过 | 96.63 秒 |
| 普通网络构建 | 23/23 组通过 | 158.36 秒 |
| ASan/UBSan 网络构建 | 23/23 组通过 | 162.83 秒 |

两次完整网络回归中的 cluster_fault 分别耗时 26.98 秒和 28.86 秒。构建日志无编译警告或错误，检查期间没有报告项目代码的地址或未定义行为错误。以上测试耗时与故障计数不是吞吐量或尾延迟 benchmark。

本轮仍限于可信本机回环网络。调度的是应用层 Raft Envelope，不模拟内核 TCP 的每个细节，不覆盖真实断电、磁盘设备故障、跨机器时钟或所有可能的网络交错。第三方 gRPC/Protobuf 仍复用 Release 依赖，ASan/UBSan 插桩范围以项目代码为主；不新增网络层 ThreadSanitizer 检查。
