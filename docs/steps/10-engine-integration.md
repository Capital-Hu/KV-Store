## 五个新增测试

### 1. 混合操作与多轮重开

用独立的 `std::map<std::string, std::string>` 保存预期结果，模型不调用引擎的 WAL 编解码或 SSTable 读取逻辑。

- 关闭缓存与 8 KiB 缓存分别运行；小缓存用于制造内存压力，不改变默认配置。
- 每种配置使用两个固定 seed，每个 seed 连续运行三轮，每轮 180 次生成操作，共 2160 次生成操作，另有设置、全量检查和收尾操作。
- 生成 Put、覆盖、Delete、Get，包含空 key、带零字节的 key、空值和二进制值。
- 自动刷盘阈值设为 2 KiB，自动合并阈值设为三张表，同时穿插手动后台请求。
- 运行中多次核对全部 32 个 key 和一个始终未写入的 key，每轮重开再检查。
- 每轮收尾刷出已有表，再留下一条未刷盘的小写入，确保下一次打开真正检验 WAL 恢复。

这是一组正确性测试，不用耗时计算吞吐量或尾延迟。

### 2. 四层读取和发布交接

先创建两张包含覆盖与删除的 SSTable，并预热缓存。暂停冻结表的后台刷盘，使以下四层同时存在：

```text
可写 MemTable
冻结 MemTable
较新 SSTable
较旧 SSTable
```

让同一个 key 在层之间出现更新、删除和重插，核对查询顺序。刷盘暂停时完成旧表合并，检查旧 reader 的缓存被清除；随后允许刷盘发布，再检查可写表中的更新仍然优先。最终刷盘、合并、重开，再次对照模型。

Gate 仅暂停后台线程已经写完 SSTable、尚未取得状态锁进行发布的位置，因此主线程还能继续读写或等待另一类后台工作。它通过条件变量等到准确位置，不靠 sleep 猜时序；异常退出也会先释放 Gate，再让 Store 等待后台线程。

### 3～5. 带成功通知的进程强杀

父进程先准备两张有重叠 key 的 SSTable，关闭 Store 后才 fork。子进程重新打开 Store，并预热磁盘块缓存，然后执行操作。

```text
子进程：Put/Delete 成功返回
                 ↓
        通过 pipe 发送这次操作的序号
                 ↓
父进程：按照序号更新自己的内存模型

子进程：走到指定协议边界，发送标记，立即 SIGKILL 整个子进程
                 ↓
父进程：确认收到全部成功通知和边界标记，确认子进程确实被 SIGKILL
                 ↓
        重新打开 Store，与独立模型逐 key 比较
```

父进程的模型在自己的进程中，不会随被测 Store 一起消失。它根据已经收到的操作成功通知更新预期结果，而非从恢复出来的数据生成答案。测试对通知顺序、数量、到达边界和退出信号都做断言；有超时和异常清理，未到达目标边界会明确失败。

| 测试 | 强杀位置 | 强杀前额外准备 |
| --- | --- | --- |
| 冻结/WAL 切换 | 新 WAL 同步；临时清单同步；rename；目录同步；内存切换，共 5 个位置 | 两张旧表及 16 次已成功的混合写入/删除 |
| 冻结表刷盘 | SSTable 写完/同步；临时清单同步；rename；目录同步；移除冻结表；删除旧 WAL，共 7 个位置 | 暂停后台刷盘，再向新 WAL 写入 16 次操作，形成新旧两份恢复状态 |
| 后台合并 | 输出写完/同步；临时清单同步；rename；目录同步；切换 reader；首次删除旧表，共 7 个位置 | 暂停合并，另外刷出一张更新的表，再向当前 WAL 写入更晚的操作 |

缓存关闭和 8 KiB 缓存各运行全部位置，因此共有 `(5 + 7 + 7) × 2 = 38` 个强杀场景。

每次恢复后先核对全部 key，再等待恢复的冻结表刷盘，检查目录只保留清单引用的数据文件。然后继续写入、删除、刷盘和合并，再换成相反的缓存配置重新打开，检查数据不依赖之前的缓存。

## 运行方法

在项目根目录执行：

```sh
cmake --build build --target engine_integration_test
./build/engine_integration_test
```

成功输出：

```text
All 5 engine integration tests passed (38 process-crash scenarios).
```

测试使用独立临时目录，只强杀自己创建的子进程；不会读取或修改手动运行 CLI 的数据。若是全新构建目录，先按 README 配置 CMake。

只运行前两个进程内场景：

```sh
./build/engine_integration_test --in-process
```

这个入口用于 ThreadSanitizer 的线程检查，不创建或强杀子进程，输出 `All 2 in-process engine integration tests passed.`。

完整回归入口仍是：

```sh
cmake --build build
ctest --test-dir build --output-on-failure
```

## 必须区分的边界

- 进程 SIGKILL 后，操作系统和设备仍在运行。因此这些测试验证进程崩溃恢复，不代替实际断电实验；rename 后的可见性也不能单独证明掉电持久性。
- 本轮在操作成功通知之后中断内部整理过程，没有模拟客户端调用执行到一半时的所有可能结果。对未收到成功的调用，不能承诺它一定没写入。
- 原有文件损坏、真实部分写入、不完整 WAL 尾部、双 WAL 校验和后台异常测试继续承担各自的故障验证。
- 此处没有事务、多 key 原子性或 Raft commit，也没有性能结论。

## 本轮遇到的 C++ 与进程概念

`Model` 是 `std::map` 的类型别名，只保存可见值；删除时从模型移除即可，模型不需要模拟引擎内部删除标记。`std::optional<std::string>` 中，nullopt 表示删除，存在的空字符串仍表示一次 Put。

`fork()` 创建的是另一个进程，父子拥有各自的内存状态；普通变量和 `shared_ptr` 不提供跨进程共享。这里用 pipe 传递操作序号。Gate 的 shared_ptr 只解决同一进程内回调的生命周期，条件变量负责线程间同步。

进程被 SIGKILL 时不会运行 C++ 析构函数，也不会执行 Store 的正常收尾，因此能检查未正常关闭时的文件协议。父进程的 RAII 清理对象则负责回收子进程、关闭管道和移除临时目录。
